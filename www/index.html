Zoraxy Cloudflare WAF plugin

Mirrors abusive clients from Zoraxy's access log and blacklist events into a Cloudflare IP List.
How this works (read this first)

What it does

  • Follows Zoraxy's access log (the current month's zr_YYYY-M.log, from the moment the plugin starts, moving to the next month's file by itself) and, if ticked, Zoraxy's own blacklist events.
  • A client IP becomes a block candidate when (1) a request looks like an exploit probe (path traversal, /etc/passwd, actuator endpoints and similar); (2) it asks for a file only scanners ask for, whatever the response status (single-page apps answer such paths with 200, so error counts alone miss those scanners): version-control folders (/.git, /.svn, /.hg), /.env, tool and cloud folders (/.aws, /.docker, /.kube, /.ssh, /.azure, /.gcloud, /.config, /.anthropic, /.vscode, /.idea), credential dotfiles (.netrc, .npmrc, .pypirc, .htpasswd, .htaccess, .bash_history, .DS_Store), files named like credentials (credentials.json, client_secret…, service-account…) and SSH keys (id_rsa, id_ed25519, id_ecdsa); or (3) it makes more than the threshold of 4xx/5xx responses within the window (default 30 in 60 seconds; see Detection thresholds). Matching is on the request path, ignoring case; /.well-known/ never matches.
  • Private, loopback, link-local and Cloudflare's own addresses are never blocked. An IP already actioned is skipped until the re-block cooldown passes (default 24 hours).
  • Two layers, independent: Cloudflare's edge (primary) and, optionally, Zoraxy's own blacklist. If one layer fails and the other works the action shows as partial, and the failing layer's reason is in the Detail column. With Also ban in Zoraxy ticked the plugin can run without Cloudflare credentials (Zoraxy layer only).
  • Blocks expire after the number of days you set (default 14; 0 keeps them forever), in both layers. The check runs hourly while live, removes at most 200 entries a run, and only removes entries this plugin created.

Off, dry run, live

  • Enabled off — nothing is acted on.
  • Enabled + Dry run — decisions are recorded and logged, but nothing is sent to Cloudflare and nothing is banned in Zoraxy. This is the safe way to watch what it would do.
  • Enabled, Dry run off (live) — the first real block creates the IP list and one WAF custom rule in Cloudflare (if they don't exist), then adds the IP to the list. Until then Cloudflare shows nothing new — that's expected.

Where to see what it's doing

  • The Recent actions table at the bottom of this page. It shows the last 200 actions and survives restarts: it is restored from zoraxy_actions.jsonl next to the plugin binary (if it is empty after a restart, look for history: lines in the journal).
  • The Zoraxy journal, which keeps the full history: journalctl -u zoraxy -f | grep -F "Zoraxy Cloudflare WAF plugin". A "logtail: alive" line appears every 30 minutes and an "expiry:" line every hour, so "running, nothing to do" can be told from "not running".

Names — two different fields

  • IP list name is the machine name Cloudflare uses inside the rule expression: letters, digits and underscores only, no spaces, up to 50 characters (default zoraxy_cf_waf_blocklist).
  • WAF rule name is just the label in Cloudflare's Security Rules list — spaces and capitals are fine. Use a name none of your own rules has. The plugin only ever edits the rule it created. If one of your rules already has exactly this name, it is left untouched, the plugin's rule is not created, and blocks are reported as errors (Test Connection warns you up front).

Good to know

  • Test Connection checks what is typed in the boxes but does not save it — click Save afterwards.
  • A changed Block action reaches Cloudflare at the next real block, not when you save.
  • Cloudflare limits how many lists an account can have (Free plans very few — a separate limit from the 5 custom rules). If it is used up, the first block fails with "maximum number of lists"; Test Connection shows your lists and warns. Free one, or point IP list name at an existing IP list that is only a block list. Never reuse an allow list: blocked IPs added to it would be let through.
  • Zoraxy-side bans only block if the access rule's blacklist is switched on and Zoraxy sees the visitor's real address (behind a tunnel, add the tunnel's addresses to Zoraxy's trusted proxies and turn on "Trust proxy headers only"). Otherwise the ban is accepted and silently does nothing.
  • Several accounts and zones. The primary account can protect up to five zones (put the extra zone IDs under the Zone ID); two more Cloudflare accounts have their own tabs, each with its own token, IP list, zones, rule name and block action. Tabs 2 and 3 have their own Enabled switch; the master Enabled and Dry run switches above apply to everything. One account failing never stops the others: the action shows as partial and says which account. Each zone needs a free custom-rule slot, and each account its own list quota.
  • There is no "unblock this IP" button: remove the address from the Cloudflare list and from the Zoraxy access rules by hand.
  • Changes to the log directory or detection thresholds need the plugin to be restarted.
Setup required. Fill in the Cloudflare section below and click Test Connection. The Enabled toggle stays locked until credentials are saved (or a test succeeds) — see https://github.com/Braedach/zoraxy-cloudflare-waf#setup (README → Setup) for how to create a correctly scoped token. Zoraxy's plugin frame blocks link clicks, so copy the address.
Behaviour
Many scanners use rented cloud addresses that are later reused by legitimate services, so a permanent block slowly becomes a false positive. Only entries this plugin added are ever removed — never ones you added by hand. Removal runs hourly and only while live (not in dry run).
Detection thresholds (log tailer — restart plugin after changing)
Cloudflare — primary account
Needs a scoped token (never the Global API Key) with exactly two permissions: Account → Account Filter Lists → Edit and Zone → WAF → Edit, scoped to this account and this zone. Create one at https://dash.cloudflare.com/profile/api-tokens → "Create Custom Token".
Both IDs are on the zone's Overview page in the Cloudflare dashboard, right-hand sidebar. They are masked like the token (safer on a shared screen) — use Show to check them; they re-hide after 15 seconds.

Applied to the one rule this plugin manages. A change takes effect on Cloudflare's side at the next real block, not when you click Save.
Cloudflare's own current limits (Free/Pro/Business, verify against your plan): 5 custom rules per zone, 10,000 items total across all custom IP lists on the account, and a 4,096-character expression limit per rule. This plugin's design (one list, one rule referencing it) keeps the rule's expression under 40 characters regardless of list size, so the character limit is never the real constraint — the list's 10,000-item cap is. The field above stops this plugin from even trying past that cap; a full list shows as skipped-list-full below instead of erroring.
Zoraxy's own blacklist (optional second layer)
Bans go into the blacklist of the access rules you tick below and expire with the setting above. Two things must be true for a ban to work: the rule's blacklist must be switched on, and Zoraxy must see the visitor's real address — behind a Cloudflare tunnel that means the address the tunnel connects from (this server's own addresses, e.g. 127.0.0.1 and its LAN IP) must be in Zoraxy's Trusted Proxies, with Trust proxy headers only switched on for the rule — including the Default rule (with it off, a rule never reads the visitor's real address). See the README ("Zoraxy's own blacklist"). Uses the API permissions Zoraxy lists for this plugin — restart Zoraxy once after installing this version.
